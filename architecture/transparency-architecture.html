ZeroBias is a transparency state machine between organizations. Two (or more) orgs enter an Engagement; inside it they exchange entangled task pairs (a demand-side requirement ↔ a supply-side satisfaction); the platform captures every exchange as a hash-chained Record; the validated state is published through a Transparency Center any scoped auditor can read. The final deliverable is an OWL + SHACL + RDF container carrying the full audit trail of a multi-party assessment — transportable as one signed package. SME Mart, Readiness Center, and Work Worlds are three UIs over that one substrate.

The one thing to understand first

Everything in this document exists to enable one deliverable: a cross-org, signable, projectable compliance-attestation record. If a design decision in any 3P app makes that final RDF/SHACL container harder to produce, it is the wrong decision (see the RDF compass, Tab 4). Read every claim through the status legend above — this system is partly shipped, partly planned, partly undecided.

The platform owns the data model and the APIs. 3P apps are standalone UIs that authenticate via the ZB SDK and call the same platform / hub / hydra APIs. None of them owns its own copy of Engagement / Project / Task — those are platform entities.

EXISTS

How scoping & RACI actually workThe Project holds the membership roster (all project members). Boards and Tasks under that Project are scoped by Project membership — the Board carries no roster of its own. Per-task RACI (assigned / accountable / approvers / notified) lives on the Task, not the Board. So: need a member roster on something? Make it a Project, not a Board. (This is why SME Mart models Vetting as a depth-3 Project — membership.) A Board config/cog panel should be future-extensible: today name/description/defaults; later gains custom-fields + activity-scoping when Board Settings lands.

Tasks

  • EXISTS platform.Task — the atomic unit. SME Mart extends via SmeMartTask. Fields: activityId (required), name, status, phase, numeric priority (1000 Critical / 500 High / 200 Normal / 100 Low), rank, code (activity prefix + org-scoped counter).

  • EXISTS ActivityLog — append-only, hash-chained log rolling up task → board → project → … → engagement. The precursor to the Record stream (Tab 4).

The mechanics

  • Demand side is a coalition. The buyer (HIS) has its primary Engagement with the seller (Goshen). The buyer also engages multiple independent 3PAO auditors, each via its own separate Buyer↔Auditor Engagement.
  • Cross-engagement linking (ResourceLink). Each auditor's project is linked into the primary Buyer↔Seller project. This is the only path by which an auditor gains data-plane access to the supplier's people / apps / devices / policies — through the primary project's boundaries.
  • Auditors are demand-side, not a third side. The supplier (auditee) is the lone supply side.
  • One SAT satisfies many REQs. A single supplier satisfaction task can satisfies-link the buyer's own requirement and one or more auditors' requirements simultaneously.

What stays sovereign
never crosses

Each party's internal Party Policy (RACI, boundaries, eval criteria), its Boundary Manager state, and its Private Execution (internal prep, scoring, cost analysis).

What we adopt · what we don't

Adopt

  • Name the model in W3C vocabulary in spec docs (instant credibility with ontology-literate audiences).
  • Publish per-engagement SHACL packages as versioned artifacts; both parties pin a version.
  • Position the Hierarchy Editor as a SHACL UI — we accidentally built one.
  • Add an RDF / JSON-LD output to the Multi-Protocol Gateway (a serialization adapter over existing infra).
  • Use PROV-O for Record provenance; the hash chain stays our differentiator on top.
  • Add ODRL + DPV shapes for engagements touching money or PII.

Don't (platform-team scope, NOT 3P frontend)

  • Don't replace AuditgraphDB with a triplestore — ZB is the schema of record.
  • Don't run full OWL reasoning in the hot path — design-time / publish-time only.
  • Don't lock to SHACL 1.2 Node Expressions (still FPWD, Jan 2026). Core + Rules + Profiling are stable.
  • Don't write the OWL/SHACL artifact before the ZB schema lands.
  • Don't build the MP-Gateway RDF endpoint or the OSCAL→SHACL binding — platform-team work.
  • Don't oversell the quantum framing externally before the substrate path is concrete.

One-sentence pitch

The W3C ontology stack — OWL 2 + SHACL 1.2 + RDF — is the language we describe our model in, not the runtime we replace it with: ZB AuditgraphDB stays the schema of record, but Requirement becomes an OWL class + SHACL NodeShape, Engagement becomes a versioned SHACL profile, the Multi-Protocol Gateway becomes RDF content-negotiation over hash-chained Records, and the Boundary becomes a System whose validated state is the projectable Hologram — giving us interoperability with every standards-compliant auditor, regulator, and enterprise platform, and a substrate-independent semantics that ports cleanly onto quantum hardware when that's ready.
